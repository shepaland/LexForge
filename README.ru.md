# LexForge

[![lexforge on npm](https://img.shields.io/npm/v/lexforge.svg)](https://www.npmjs.com/package/lexforge)
[![license MIT](https://img.shields.io/npm/l/lexforge.svg)](LICENSE)

**Русский** · [English](README.md)

Конвейер spec-driven разработки для кодовых агентов, с воротами, которые агент не обойдёт. Девять
скиллов ведут изменение от запроса пользователя до архивированной спеки, а `lexforge verify`
отвечает кодом возврата, сделана работа или нет: заявление о готовности, за которым нет свежего
вывода команд, не проходит.

## Быстрый старт

```bash
npm install -g lexforge       # скиллы зовут команду этим именем на PATH
lexforge init --tools claude  # agents · claude · codex · cursor · opencode
lexforge doctor               # шесть условий, каждое названо с находкой или без
```

Дальше попросите агента о работе обычными словами — «добавь X», «почини Y». Скилл `lexforge`
называет класс работы, и конвейер стартует оттуда; все четыре шага целиком — в разделе
[Первый запуск](#первый-запуск).

LexForge собран из двух систем: артефакты и проверяемую структуру требований он берёт
у **OpenSpec**, процессные ворота и поведенческие правила для агента — у **superpowers**.

## Что даёт объединение

OpenSpec и superpowers решают разные половины одной задачи, и каждая половина ломается без второй.
OpenSpec описывает шаги, но ничем не мешает их обойти. superpowers держит агента в дисциплине,
но после слияния ветки от работы не остаётся ни одного документа, который кто-то потом прочитает.

### Сильные стороны, которые взяты

| Донор | Сильная сторона | Где в LexForge |
| --- | --- | --- |
| OpenSpec | Изменение идёт через артефакты `proposal → specs → design → tasks` | схема изменения задаёт порядок, `lexforge status` показывает очередь |
| OpenSpec | Требования записаны так, что их проверяет программа: `### Requirement:` с одним или несколькими `#### Scenario:` на `WHEN`/`THEN` | `lexforge validate --strict` |
| OpenSpec | Спеки живут в репозитории, дельта вливается при архивации | `lexforge/specs/`, `lexforge archive` |
| OpenSpec | Инструкция к артефакту собирается вместе с контекстом и правилами проекта | `lexforge instructions <artifact> --change <name>` |
| OpenSpec | Изменение без правки поведения не обязано выдумывать требование | `skip_specs: true` в `.lexforge.yaml`, статус `skipped` |
| superpowers | Класс работы называется до проектирования | скилл `lexforge` выбирает схему: spike, `bounded`, `spec-driven` |
| superpowers | Вопросы по одному и 2–3 подхода с рекомендацией до записи артефакта | `lexforge-propose` |
| superpowers | TDD с наблюдённым падением теста | `lexforge-apply` внутри каждой задачи |
| superpowers | Ревью субагентом с узким контекстом, а не всей историей сессии | `lexforge-apply` между задачами |
| superpowers | Заявление о готовности подкрепляется свежим выводом команды | `lexforge evidence record`, `check evidence`, `lexforge-verify` |
| superpowers | Причина бага ищется до предложения фикса | `lexforge-debug` |
| superpowers | Формат текста, проверенный на живых агентах: Iron Law, таблица «отговорка → реальность», Red Flags | текстовая часть каждого `SKILL.md` |

### Недостатки, которые закрыты

| Донор | Недостаток | Что вместо него в LexForge |
| --- | --- | --- |
| OpenSpec | Ни одного поведенческого запрета для агента: шаги описаны, обойти их ничто не мешает | ворота считают состояние сами: `status` отдаёт `blocked`, `check plan`, `check evidence` и `verify` отвечают кодом возврата, флага «пропустить правило» нет ни у одной команды |
| OpenSpec | `proposal.md` пишется прямо из первого сообщения пользователя, и непроверенное понимание задачи закрепляется в артефакте | `lexforge-propose` задаёт вопросы по одному и показывает подходы с рекомендацией до того, как запишет раздел «Why» |
| OpenSpec | Сказать «готово» можно, не запустив ни одной проверки | `evidence record` сам выполняет команду метки и пишет штамп с кодом возврата, коммитом и отпечатком рабочего дерева; произвольную команду аргументом не принимает |
| OpenSpec | `SKILL.md` собирается функцией из TypeScript, и правка скилла требует пересборки | скиллы лежат файлами и правятся как текст |
| superpowers | После слияния ветки не остаётся долговременного документа: дизайн лежит в `docs/superpowers/specs/` и больше никем не читается | дельта вливается в `lexforge/specs/<capability>/spec.md`, изменение целиком уходит в `lexforge/changes/archive/` |
| superpowers | Требования пишутся прозой, программа их не проверит | дельта-спеки с `Requirement` и `Scenario`, проверка `validate --strict` |
| superpowers | Дисциплина держится только текстом, и агент находит для неё отговорку | часть правил перенесена в код CLI: план без заполнителей, покрытие требований задачами и свежесть штампов проверяет команда, а не убеждение |
| superpowers | У скиллов нет общего состояния: скилл не знает, что уже сделано | `lexforge status --change <name> --json` отдаёт статусы артефактов, `blockedBy` и `isPlanningComplete`; каждый скилл начинает с этого вызова |
| superpowers | Порядок из четырнадцати скиллов общего назначения агент собирает сам | порядок задан схемой изменения, скилл в статусе `blocked` останавливается и называет неготовый артефакт |

Два дублирования срезаны. Дизайн живёт только в каталоге изменения, отдельный `docs/superpowers/specs/`
не заводится. План не становится вторым файлом: `tasks.md` пишется по требованиям writing-plans
и служит планом.

## Артефакты, ворота, архив

Каждое изменение живёт в каталоге `lexforge/changes/<name>/`: там лежат `proposal.md`,
дельта-спеки, `design.md`, `tasks.md`. Порядок задаёт схема изменения. Артефакт со статусом
`blocked` не пишется, пока не готов тот, от которого он зависит. Очередь агент читает командой
`lexforge status --change <name> --json`.

Ворота считают состояние работы сами. `lexforge check plan --change <name>` ищет в плане
незаписанные задачи: заполнители шаблона, ссылки на соседнюю задачу, требование дельты без задачи.
`lexforge evidence record --change <name> --label <label>` запускает команду проверки, описанную
проектом, и записывает штамп с кодом возврата, коммитом и отпечатком рабочего дерева.
`lexforge check evidence --change <name>` сверяет штампы с кодом на диске, поэтому правка после
прогона делает штамп несвежим. `lexforge verify --change <name>` собирает эти проверки перед
завершением работы, но штампы он только читает: команды проверок запускает `evidence record`,
и снять свежий штамп надо до вызова `verify`. Флага, который отключает правило или понижает
находку, нет ни у одной команды.

`lexforge archive <change>` вливает дельту в `lexforge/specs/<capability>/spec.md` и переносит
каталог изменения в `lexforge/changes/archive/<дата>-<name>/`. В репозитории остаются спеки,
описывающие поведение выпущенного продукта, и архив изменения целиком: предложение, дизайн, план
и штампы прогонов.

## Требования

| Что нужно | Значение |
| --- | --- |
| Node.js | не ниже 20.19.0, версия из поля `engines` пакета |
| npm | тот, что поставлен вместе с Node |
| git | репозиторий хотя бы с одним коммитом; без него `evidence record`, `check evidence`, `verify` и `archive` отвечают кодом `2` |
| Агент | один из пяти рантаймов таблицы установки |
| Операционная система | прогоны шли на macOS; на Linux и Windows пакет не проверяли |

Команда `lexforge init` репозитория не требует и не создаёт. Без `.git` она заводит рабочее
пространство и называет ворота, которым репозиторий понадобится.

## Установка

Пакет опубликован в npm под именем [`lexforge`](https://www.npmjs.com/package/lexforge).
Глобальная установка кладёт команду в `PATH`, и скиллы зовут её по имени:

```bash
npm install -g lexforge
```

`lexforge --version` печатает установленную версию и подтверждает, что имя разрешилось.

Установка в зависимости проекта закрепляет версию за проектом, и тогда команду зовут через `npx`:

```bash
npm install --save-dev lexforge
npx lexforge --version
```

Два способа не равноправны. Скиллы обращаются к команде по имени `lexforge`, и `lexforge doctor`
ищет это имя в `PATH`: при установке только в `devDependencies` он даёт находку
`path-not-resolved`, а при двух установках сразу, глобальной и проектной, находку
`path-multiple-installs`, потому что вызов уходит не в тот пакет, который отвечает.

Сами скиллы ставит `lexforge init --tools <список>`, имена через запятую. Флаг `--scope project`
(по умолчанию) кладёт их в каталог проекта, `--scope user` в домашний каталог. Флаг
`--language <code>` называет язык, на котором проект пишет артефакты. Каждый рантайм держит свои
скиллы у себя:

| Рантайм | Каталог в проекте | Каталог пользователя |
| --- | --- | --- |
| `agents` | `.agents/skills` | `~/.agents/skills` |
| `claude` | `.claude/skills` | `~/.claude/skills` |
| `codex` | `.codex/skills` | `~/.codex/skills` |
| `cursor` | `.cursor/skills` | `~/.cursor/skills` |
| `opencode` | `.opencode/skills` | `~/.config/opencode/skills` |

Имя `agents` — общий каталог, который читают сразу несколько агентов.

## Первый запуск

Четыре шага от пустого каталога до первого изменения. Ни один не требует править файлы руками.

### 1. Поставить пакет

```bash
npm install -g lexforge
```

### 2. Завести рабочее пространство и поставить скиллы

```bash
lexforge init --tools claude
```

Команда печатает список созданного: `lexforge/config.yaml`, `lexforge/specs/`,
`lexforge/changes/archive/` и девять каталогов скиллов в `.claude/skills/`. Следующим шагом она
называет `lexforge doctor`.

Вызов без `--tools` заводит рабочее пространство, скиллов не ставит и перечисляет имена
рантаймов, чьи каталоги уже есть в проекте или в домашнем каталоге. Выбор остаётся за человеком.

### 3. Проверить установку

```bash
lexforge doctor
```

Шесть условий, каждое названо и с находкой, и без неё:

```
OK    Workspace and configuration
OK    Verification labels
OK    Installed skills
OK    Command name on PATH
OK    Git repository
OK    Node version
Next step: installation is healthy. Ask your agent to start work, for example: lexforge new change <name>
```

Сразу после установки проверка даст две находки и код `1`. `lexforge init` не создаёт репозиторий
git и не заполняет раздел `verification` в конфигурации, а воротам нужно и то, и другое.
Репозиторий заводится через `git init` и первый коммит, метки проверок дописываются
в `lexforge/config.yaml`:

```yaml
verification:
  tests: npm test
  lint: npm run lint
```

Имя метки пишется строчными буквами и дефисами.
`lexforge evidence record --change <name> --label tests` выполнит её команду из корня рабочего
пространства.

### 4. Попросить агента о работе

Дальше команды зовёт агент. На запрос построить, добавить или починить что-то он входит через
скилл `lexforge`, называет класс работы и заводит изменение командой
`lexforge new change <name>`.

## Девять скиллов

Скилл выбирает сам агент по строке `description` в шапке `SKILL.md`. Планирование ведут пять
скиллов.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge` | Просят что-то построить, добавить, починить или разобрать, и ни одно изменение этого не покрывает | Названный класс работы и заведённое изменение с нужной схемой |
| `lexforge-propose` | Просят предложение, или `lexforge status` показывает артефакт `proposal` в статусе `ready` | `proposal.md` из ответов пользователя: причина, выбранный подход, границы |
| `lexforge-spec` | Просят требования и сценарии, или `lexforge validate` находит дефект в дельта-спеке | Дельта-спеки по возможностям с требованиями и сценариями `WHEN`/`THEN` |
| `lexforge-design` | Просят описать решения и их цену, и изменение идёт по схеме `spec-driven` | `design.md`, согласованный с пользователем по одному разделу |
| `lexforge-plan` | Просят план, список задач или разбивку, или `lexforge validate` находит дефект в `tasks.md` | `tasks.md`, где каждая задача называет файл и команду проверки |

Каждый из пяти начинает с `lexforge status --change <name> --json` и смотрит на статус своего
артефакта: работать позволяет только `ready`. На `blocked` скилл называет неготовые артефакты
из `blockedBy` и останавливается. Ветки «предупредить и всё-таки записать файл» нет: срок, размер
правки и просьба пропустить артефакт закрытые ворота не открывают.

Вторую половину конвейера ведут четыре скилла.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge-apply` | Артефакты написаны или пропущены, просят реализовать | Задачи плана, закрытые по одной: падающий тест, минимальная реализация, ревью субагентом, штамп прогона |
| `lexforge-verify` | Реализация закончена, до архивации | Отчёт по трём измерениям с уровнями `CRITICAL`, `IMPORTANT`, `MINOR`; одна находка `CRITICAL` останавливает архивацию |
| `lexforge-archive` | Отчёт проверки без находок `CRITICAL`, просят закрыть изменение | Дельта в `lexforge/specs/`, каталог изменения в архиве, вопрос пользователю о судьбе ветки |
| `lexforge-debug` | Падает тест, ломается сборка, код ведёт себя не так, как ожидали | Названная причина, падающий тест на баг, одна правка в точке причины |

Скиллы реализации читают в том же ответе поле `isPlanningComplete`: пока хоть один артефакт
не написан и не пропущен, работа не начинается. `lexforge-debug` этого блока не несёт, потому
что баг случается и в проекте, где рабочего пространства LexForge нет.

Правка установленного скилла не держится. `lexforge doctor` сверяет файл с тем, что несёт пакет,
побайтно, а следующий `lexforge init` возвращает поставляемый текст. Правила проекта задаются
разделами `context` и `rules` в `lexforge/config.yaml`, откуда попадают в инструкцию к артефакту,
которую отдаёт `lexforge instructions`.

## Команды и коды возврата

| Команда | Что делает |
| --- | --- |
| `lexforge init` | Заводит рабочее пространство `lexforge/` и ставит скиллы для перечисленных рантаймов; `--tools`, `--scope`, `--language` |
| `lexforge doctor` | Проверяет, здорова ли локальная установка |
| `lexforge new change <name>` | Создаёт `lexforge/changes/<name>/` вместе с `.lexforge.yaml`; `--schema` берёт схему, отличную от умолчания проекта |
| `lexforge status` | Показывает статус артефактов одного изменения или список всех активных; без `--change` перечисляет активные |
| `lexforge instructions <artifact> --change <name>` | Отдаёт шаблон, контекст, правила и инструкцию для одного артефакта |
| `lexforge validate <change>` | Проверяет артефакты и требования изменения; `--strict` добавляет проверки полноты |
| `lexforge check plan --change <name>` | Ищет в плане изменения незаписанную работу |
| `lexforge check evidence --change <name>` | Сверяет штампы изменения с кодом на диске; `--require` сужает список меток |
| `lexforge evidence record --change <name> --label <label>` | Запускает команду одной метки проверки и записывает штамп |
| `lexforge verify --change <name>` | Проверяет изменение перед тем, как работу назовут законченной |
| `lexforge archive <change>` | Вливает дельту изменения в спеки и переносит его каталог в архив |

Каждая команда из таблицы принимает флаг `--json`. С ним на стандартный вывод уходит один
документ JSON и ничего кроме него, а строки для человека печатаются в поток ошибок. Формулировки
человеческого вывода меняются от версии к версии, имена полей JSON и коды возврата остаются
прежними.

| Код | Когда |
| --- | --- |
| `0` | Команда отработала, находок нет |
| `1` | Команда отработала и нашла нарушение: незакрытую зависимость, требование без сценария, оставшийся заполнитель шаблона |
| `2` | Команду нельзя выполнить: неизвестный аргумент, отсутствующее изменение, нет рабочего пространства, нет репозитория git |

Других кодов нет. Код `1` говорит о проблеме в проекте, код `2` о неверном вызове.

У `lexforge doctor` одно отличие. Отсутствие рабочего пространства для него находка, поэтому он
отвечает кодом `1`, а не `2`. Это состояние установки, о котором его и спрашивают.

## Что коммитить

| Путь | Куда |
| --- | --- |
| `lexforge/config.yaml` | В репозиторий: схема, контекст, правила артефактов и метки проверок нужны всей команде |
| `lexforge/specs/` | В репозиторий: спеки описывают поведение выпущенного продукта |
| `lexforge/changes/<name>/` вместе с `evidence.json` | В репозиторий: штамп привязан к коммиту, и в ревью видно, на чём он снят |
| `lexforge/changes/archive/` | В репозиторий: закрытые изменения с их артефактами и штампами |
| Каталоги скиллов рантайма и `lexforge-install.json` рядом с ними | Локально: их пишет `lexforge init`, и на другой машине их вернёт та же команда |

`evidence.json` меняется на каждом прогоне, поэтому два человека, работающие над одним изменением
параллельно, получат на нём конфликт слияния.

## Границы

Три вещи LexForge не проверяет, и о них лучше знать заранее.

`check plan` ищет заполнители регулярными выражениями. Формулировка вроде «добавить обработку
ошибок», написанная своими словами, в список шаблонов не попадёт. Набор расширяется по находкам.

Свежесть штампа привязана к коммиту и отпечатку рабочего дерева. Правка, сделанная после прогона,
делает штамп несвежим, но обратное неверно: штамп не говорит, что покрытие достаточное.

Согласованность реализации с решениями из `design.md` машина не считает. Если агент отступил
от дизайна, поймает это только скилл `lexforge-verify`, то есть тот же агент.
