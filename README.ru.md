# LexForge

[![lexforge on npm](https://img.shields.io/npm/v/lexforge.svg)](https://www.npmjs.com/package/lexforge)
[![CI](https://github.com/shepaland/LexForge/actions/workflows/ci.yml/badge.svg)](https://github.com/shepaland/LexForge/actions/workflows/ci.yml)
[![license MIT](https://img.shields.io/npm/l/lexforge.svg)](LICENSE)

**Русский** · [English](README.md)

Конвейер spec-driven разработки для кодовых агентов, с воротами, которые агент не обойдёт. Девять
скиллов ведут изменение от запроса до архивированной спеки, а `lexforge verify` отвечает кодом
возврата, сделана работа или нет: заявление о готовности без свежего вывода команд не проходит.

![Агент говорит, что изменение готово; `lexforge verify` отвечает кодом 1, пока проверки не запущены](https://raw.githubusercontent.com/shepaland/LexForge/main/docs/media/verify.ru.gif)

Агент написал код и отметил все галочки. `verify` отвечает `1`: в реестре нет штампа ни для одной
проверки. `evidence record` запускает команду сам и пишет штамп, и только тогда `verify` отвечает
`0`. Это изменение лежит в каталоге [`examples/notes`](examples/notes).

LexForge собран из двух систем: артефакты и проверяемую структуру требований он берёт у
**OpenSpec**, ворота и поведенческие правила для агента — у **superpowers**.

## Быстрый старт

```bash
npm install -g lexforge       # скиллы зовут команду этим именем на PATH
lexforge init --tools claude  # agents · claude · codex · cursor · opencode
lexforge doctor               # шесть условий, каждое названо с находкой или без
```

Дальше попросите агента о работе обычными словами — «добавь X», «почини Y». Скилл `lexforge`
называет класс работы, и конвейер стартует оттуда; шаги целиком — в разделе [Первый
запуск](#первый-запуск).

## Поддерживаемые платформы

| Что нужно | Значение |
| --- | --- |
| Операционная система | Linux, macOS и Windows — набор тестов проходит на всех трёх в CI |
| Node.js | не ниже 20.19.0, версия из поля `engines`; в CI 20.19 и 22 |
| Рантайм агента | `agents`, `claude`, `codex`, `cursor`, `opencode` |
| git | репозиторий хотя бы с одним коммитом; без него `evidence record`, `check evidence`, `verify` и `archive` отвечают кодом `2`. Команде `init` не нужен |

Windows — полноправная система, а не «вроде работает»: файл читается с любым переводом строки,
пути в ответах приходят с `/`, `doctor` ищет имя команды по `PATHEXT`, здоровая установка
считается одной.

## Что даёт объединение

Каждая система решает половину задачи и без второй ломается. OpenSpec описывает шаги, но не мешает
агенту их обойти; superpowers держит агента в дисциплине, но после слияния ветки не остаётся
ничего, что кто-то потом прочитает.

| Взято | Что LexForge с этим делает |
| --- | --- |
| OpenSpec: порядок `proposal → specs → design → tasks` | его задаёт схема, `status` показывает очередь, артефакт `blocked` не пишется |
| OpenSpec: требования, которые проверит программа | `### Requirement:` со сценариями `WHEN`/`THEN`, проверяет `validate --strict` |
| OpenSpec: спеки, которые остаются в репозитории | дельта вливается на `archive`, изменение уходит в `lexforge/changes/archive/` |
| superpowers: класс работы назван до дизайна | скилл `lexforge` выбирает схему: spike, `bounded`, `spec-driven` |
| superpowers: TDD и ревью субагентом | `lexforge-apply` проводит тест и независимое ревью каждого поведенческого цикла |
| superpowers: нет готовности без свежего вывода | `evidence record` сам запускает команду и штампует коммит и дерево |

Остального не было ни у одной. План без заполнителей, покрытие требований задачами и свежесть
штампа проверяет команда, а не уговоры, и флага, отключающего правило, нет ни у одной команды.
Состояние скиллы делят через `lexforge status --change <name> --json`, поэтому ни один не гадает,
что уже сделано. Срезаны и два дублирования: дизайн живёт только в каталоге изменения, а планом
служит `tasks.md`.

## Как это работает

```
запрос: «построй X», «добавь Y», «почини Z»
    │
    ▼
скилл lexforge — называет класс работы  ──►  spike: ответ, изменение не заводится
    │  bounded · spec-driven
    ▼
lexforge new change <name>
    │
    ▼
ПЛАНИРОВАНИЕ — код проекта не трогают. Каждый скилл сначала зовёт
lexforge status --change <name> --json: работает при `ready`, стоит при `blocked`.
    lexforge-propose ──► proposal.md          по одному вопросу за раз
    lexforge-spec    ──► specs/<cap>/spec.md  validate --strict → 0
    lexforge-design  ──► design.md            согласуется по разделам
    lexforge-plan    ──► tasks.md             check plan → 0
    │
    ▼  isPlanningComplete = true
РЕАЛИЗАЦИЯ — lexforge-apply, по поведенческим циклам (процесс версии 2)
    cycle start ──► RED ──► реализация ──► GREEN ──► ревью ──► cycle close
    на границе волны: evidence record
    задача вышла за спеку → остановиться и спросить пользователя
    │
    ▼
lexforge-verify · lexforge verify --change <name>
    есть CRITICAL → назад в lexforge-apply
    нет CRITICAL  → lexforge archive <change>
                    дельта    → lexforge/specs/<capability>/spec.md
                    изменение → lexforge/changes/archive/<дата>-<name>/

вне конвейера: lexforge-debug — падающий тест, сломанная сборка, неожиданное
поведение; работает и без рабочего пространства LexForge.
```

## Артефакты, ворота, архив

В каталоге `lexforge/changes/<name>/` лежат `proposal.md`, дельта-спеки, `design.md` и `tasks.md`,
в порядке, заданном схемой.

Ворота считают состояние работы сами. `check plan` ищет в плане незаписанную работу: заполнители,
ссылки на соседнюю задачу, требование дельты без задачи, раздел, где строка `Depends on:`
пропущена, повторена или называет то, что не читается, задачу без ярлыка группы, две группы одного
раздела с общим файлом и план, оставивший разделы внутри `tasks.md` вместо ссылки на файл каждого.
В процессе версии 1 `evidence red` запускает команду одной задачи и записывает падающий прогон по её номеру, а `verify`
называет каждую закрытую задачу, которая пишет продуктовый код без такой записи.
`evidence record` запускает команду
проверки проекта и штампует её кодом возврата, коммитом и отпечатком рабочего дерева.
`check evidence` сверяет штампы с кодом на диске, и правка после прогона делает штамп несвежим.
`verify` собирает эти проверки, но штампы только читает: свежий надо снять до вызова.
В процессе версии 2 он также проверяет закрытие циклов, записи ревью и совпадение текущих
файлов с последними проверенными снимками.

`verify` и `archive` читают ещё реестр дефектов проекта, `lexforge/defects.json`: открытая
запись уровня `critical` или `important` по изменению останавливает обе команды так же, как
несвежий штамп, а открытая запись `minor` не останавливает ничего. `lexforge defect record
--change <name> --level <level> --file <path> --line <n> --summary <text>` добавляет запись,
`lexforge defect close <id>` отмечает её исправленной, а `lexforge defect list` читает реестр
обратно, сужая его по `--change` и `--open`. Реестр хранит все записи, открытые и закрытые,
и запись переживает изменение, в котором её нашли.

`archive` вливает дельту в `lexforge/specs/<capability>/spec.md`, а каталог изменения переносит
в `lexforge/changes/archive/<дата>-<name>/`. В репозитории остаются спеки выпущенного поведения
и само изменение со штампами прогонов.

## Установка

Глобальная установка из [npm](https://www.npmjs.com/package/lexforge) кладёт команду в `PATH` —
так её зовут скиллы. Установка в проект закрепляет версию и работает через `npx`:

```bash
npm install --save-dev lexforge && npx lexforge --version
```

Два способа не равноправны. `doctor` ищет имя `lexforge` в `PATH`: при установке только
в `devDependencies` он даёт находку `path-not-resolved`, при двух установках сразу —
`path-multiple-installs`: вызов уходит не в тот пакет, который отвечает.

Скиллы ставит `lexforge init --tools <список>`, имена через запятую: `--scope project`
(по умолчанию) кладёт их в проект, `--scope user` — в домашний каталог, `--language <code>`
задаёт язык артефактов. Каждый рантайм держит скиллы у себя:

| Рантайм | Каталог в проекте | Каталог пользователя |
| --- | --- | --- |
| `agents` | `.agents/skills` | `~/.agents/skills` |
| `claude` | `.claude/skills` | `~/.claude/skills` |
| `codex` | `.codex/skills` | `~/.codex/skills` |
| `cursor` | `.cursor/skills` | `~/.cursor/skills` |
| `opencode` | `.opencode/skills` | `~/.config/opencode/skills` |

Имя `agents` — общий каталог, который читают сразу несколько агентов.

## Первый запуск

### 1. Завести рабочее пространство и поставить скиллы

```bash
lexforge init --tools claude
```

Команда печатает созданное: `lexforge/config.yaml`, `lexforge/specs/`, `lexforge/changes/archive/`
и девять каталогов скиллов. Без `--tools` скиллов не ставит, а перечисляет рантаймы, чьи каталоги
уже есть: выбор за человеком.

### 2. Проверить установку

```bash
lexforge doctor
```

```
OK    Workspace and configuration
OK    Verification labels
OK    Installed skills
OK    Command name on PATH
OK    Git repository
OK    Node version
Next step: installation is healthy. Ask your agent to start work, for example: lexforge new change <name>
```

Сразу после установки будут две находки и код `1`: `init` не создаёт репозиторий git и не
заполняет раздел `verification`, а воротам нужно и то, и другое. Репозиторий даёт `git init`
и первый коммит, метки дописываются в `lexforge/config.yaml`:

```yaml
verification:
  tests: npm test
  lint: npm run lint
```

Имя метки пишется строчными буквами и дефисами, а `evidence record --label tests` выполнит её
команду из корня рабочего пространства. Дальше команды зовёт агент.

## Назначение моделей

Стадии одного change стоят разных моделей: написать proposal — не то же самое, что пройти
`tasks.md` задача за задачей. Каждый скилл открывается блоком модели — строкой на провайдера — и
читает её, когда проект не назвал ни одной, — репозиторий работает с первого запуска на том агенте,
который его открыл. Планирующие скиллы и проверка завершения называют сильную модель
провайдера, реализация и отладка — среднюю, архивация не называет никакой.

Слово проекта сильнее. Раздел `models` файла `lexforge/config.yaml` держит по записи на
рантайм, и стадия разрешается по записи того рантайма, из которого пришёл вызов:

```yaml
models:
  tools:
    claude:
      provider: anthropic
      model: claude-opus-5
    codex:
      provider: openai
      model: gpt-5.6-sol
  providers:
    anthropic:
      - claude-opus-5
      - claude-sonnet-5
```

Запись решает целиком: верхний уровень для рантайма с записью не читается, поэтому два агента
разных вендоров работают в одном репозитории и ни один не тянется к чужой модели. Рантайм без
записи берёт верхний `default`, а проект, не назвавший ни того ни другого, оставляет каждый
скилл на модели из его блока модели.

`lexforge init --tools claude,codex` пишет запись каждому названному рантайму со своим
вендором — `claude` для Anthropic, `codex` для OpenAI — и не пишет `default`. `cursor`,
`opencode` и `agents` работают поверх нескольких вендоров, поэтому их модели называете вы.

Каталог `providers` заполняется из списка, который поставляется с установленной версией, и
дальше принадлежит проекту: добавьте провайдера или имя модели прямо в файле, и они считаются
известными без выпуска новой версии. Имена по каталогу не сверяются, поэтому модель, вышедшая
после установки, работает в день выхода.

Рантайм называет вызывающий, угадывания нет:
`lexforge instructions <artifact> --change <name> --tool codex --json` и
`lexforge status --change <name> --tool codex --json` отдают провайдера и модель этого
рантайма. Для выбора рантайма LexForge не читает переменные окружения. Вызов без имени рантайма — вызов,
чей рантайм неизвестен, и он разрешается по верхнему уровню раздела. Скилл на другой модели
передаёт работу субагенту, запущенному на назначенной; скилл, который до неё не дотягивается,
останавливается и говорит об этом.

### Проект, поставленный до этой версии

Ничего не меняется, пока вы сами не попросите. `lexforge init` не трогает существующий
`config.yaml`, включая отсутствующий раздел `models`, а проект без раздела получает пустое
назначение: ни одна команда не отказывает, каждый скилл остаётся на модели своего блока. Ключ,
оставшийся от ролей, которые этот выпуск удалил, не читается, и отказа из-за него нет.
Включается раздел одной правкой — вставьте блок выше в `lexforge/config.yaml` и впишите свои
имена.

### Передача в каждом рантайме

Гейт не называет рантайм: одни и те же девять скиллов ставятся в пять разных. Может ли скилл
запустить субагента на названной модели — дело самого рантайма.

| Рантайм | Выбор модели для субагента |
|---|---|
| `claude` | Подтверждено: субагент запускается на названной модели, передача работает так, как описано. |
| `agents`, `codex`, `cursor`, `opencode` | Здесь не подтверждено. Пока прогон не показал обратного, оставьте такой рантайм без записи в разделе `models`: его агенты остаются на модели, которую называют их скиллы, и передача не нужна. |

## Девять скиллов

Скилл агент выбирает сам, по строке `description` в `SKILL.md`. Планирование ведут пять.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge` | Просят построить, добавить или починить то, чего не покрывает ни одно изменение | Названный класс работы, заведённое изменение с нужной схемой |
| `lexforge-propose` | Просят предложение, или `proposal` в статусе `ready` | `proposal.md`: причина, выбранный подход, границы |
| `lexforge-spec` | Просят требования, или `validate` находит дефект в дельта-спеке | Дельта-спеки по возможностям со сценариями `WHEN`/`THEN` |
| `lexforge-design` | Просят описать решения, схема `spec-driven` | `design.md`, согласованный по одному разделу |
| `lexforge-plan` | Просят план, или `validate` находит дефект в `tasks.md` | `tasks.md`, где задача называет файл и команду проверки |

Ветки «предупредить и всё-таки записать файл» нет: ни срок, ни размер правки, ни просьба
пропустить артефакт закрытые ворота не открывают.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge-apply` | Артефакты готовы, просят реализовать | Поведенческие циклы с RED/GREEN, независимым ревью и доказательствами; прежний цикл задач для версии 1 |
| `lexforge-verify` | Реализация закончена, до архивации | Машинные проверки и ревью соответствия требованиям; открытые `CRITICAL` и `IMPORTANT` блокируют готовность |
| `lexforge-archive` | В отчёте нет находок `CRITICAL` | Дельта в `lexforge/specs/`, изменение в архиве, вопрос о судьбе ветки |
| `lexforge-debug` | Падает тест, ломается сборка, код ведёт себя не так | Названная причина, падающий тест на баг, одна правка в точке причины |

Скиллы реализации читают поле `isPlanningComplete`: пока хоть один артефакт не написан и не
пропущен, работа не начинается. `lexforge-debug` этого блока не несёт: баг случается и там, где
рабочего пространства LexForge нет.

Правка установленного скилла не держится: `doctor` сверяет файл с поставляемым побайтно,
а следующий `init` восстанавливает поставляемую версию. Правила проекта задаются разделами `context` и `rules`
в `lexforge/config.yaml`, откуда попадают в `lexforge instructions`.

## Команды и коды возврата

| Команда, после `lexforge` | Что делает |
| --- | --- |
| `init` | Заводит рабочее пространство `lexforge/` и ставит скиллы; `--tools`, `--scope`, `--language` |
| `doctor` | Проверяет, здорова ли локальная установка |
| `new change <name>` | Создаёт каталог изменения, `.lexforge.yaml` и `workflow.json`; `--schema` меняет схему проекта |
| `status` | Показывает статус артефактов изменения или список активных |
| `instructions <artifact> --change <name>` | Отдаёт шаблон, контекст, правила и инструкцию |
| `validate <change>` | Проверяет артефакты и требования; `--strict` добавляет проверки полноты |
| `check plan --change <name>` | Ищет в плане незаписанную работу |
| `check evidence --change <name>` | Сверяет штампы с кодом на диске; `--require` сужает список меток |
| `evidence record --change <name> --label <label>` | Запускает команду одной метки и пишет штамп |
| `evidence red --change <name> --task <id> --command <cmd>` | Запускает команду одной задачи и записывает падающий прогон |
| `context --change <name> --task <id>` | Возвращает контекст текущего цикла и ссылки на источники; `--max-bytes` ограничивает размер без усечения |
| `workflow migrate --change <name> --to 2` | Показывает отчёт с `--dry-run`; после разрешения выполняет восстанавливаемую миграцию |
| `cycle start --change <name> --cycle <id> --executor <identity>` | Сохраняет исходные файлы до правок |
| `cycle run --change <name> --cycle <id> --phase red\|green` | Запускает команду из карты цикла и записывает доказательства |
| `cycle review --change <name> --cycle <id> --file <path>` | Принимает отчёт независимого ревьюера для текущего GREEN |
| `cycle close --change <name> --cycle <id>` | Проверяет готовность цикла и сохраняет состояние продолжения |
| `cycle restart --change <name> --cycle <id> --executor <identity>` | Начинает новую попытку с историей и прежней базой ревью |
| `resume --change <name>` | Восстанавливает состояние из первичных записей |
| `verify --change <name>` | Проверяет изменение перед тем, как работу назовут готовой |
| `archive <change>` | Вливает дельту в спеки и переносит изменение в архив |
| `defect record --change <name>` | Записывает дефект по изменению; `--level`, `--file`, `--line`, `--summary` |
| `defect close <id>` | Отмечает записанный дефект исправленным |
| `defect list` | Выводит записанные дефекты; `--change` и `--open` сужают список |

Каждая команда принимает `--json`: на стандартный вывод уходит один документ JSON и ничего кроме,
строки для человека — в поток ошибок. Формулировки человеческого вывода меняются от версии
к версии, имена полей JSON и коды возврата — нет.

| Код | Когда |
| --- | --- |
| `0` | Команда отработала, находок нет |
| `1` | Команда нашла нарушение: незакрытую зависимость, требование без сценария, заполнитель |
| `2` | Команду нельзя выполнить: неизвестный аргумент, нет изменения, нет рабочего пространства или репозитория |

Код `1` сообщает о найденном нарушении или непринятом прогоне. Код `2` означает, что
вызов нельзя выполнить; сюда входят устаревшие доказательства и незавершённые условия цикла. У `doctor` одно
отличие: отсутствие рабочего пространства для него находка, поэтому он отвечает `1`, а не `2`.

## Что коммитить

| Путь | Куда |
| --- | --- |
| `lexforge/config.yaml` | В репозиторий: схема, контекст, правила и метки нужны всей команде |
| `lexforge/specs/` | В репозиторий: спеки описывают поведение продукта |
| `lexforge/changes/<name>/` с `evidence.json` | В репозиторий: штамп привязан к коммиту, и в ревью видно, на чём он снят |
| `lexforge/changes/archive/` | В репозиторий: закрытые изменения с артефактами и штампами |
| `lexforge/defects.json` | В репозиторий: запись переживает изменение, в котором её нашли, а ревью должно видеть, что ещё открыто |
| Каталоги скиллов рантайма и `lexforge-install.json` | Локально: на другой машине их вернёт `init` |

`evidence.json` меняется на каждом прогоне, поэтому два человека, работающие над одним изменением
параллельно, получат на нём конфликт слияния.

## Предел длины файла

Каждый исходный и тестовый файл, который затрагивает изменение, держится в пределе строк: по
умолчанию 400, его задаёт `file_limit.lines` в `lexforge/config.yaml`, счёт как у `wc -l`, и файл
ровно на 400 строках остаётся в пределе. Набор покрытых файлов задаёт `file_limit.include` там же:
24 расширения исходников и тестов по умолчанию (`**/*.ts`, `**/*.py`, `**/*.vue` и другие), свой
`include` проекта заменяет этот список, а не добавляется к нему. Markdown, JSON, YAML и lock-файлы
вне предела по умолчанию. Сгенерированный или заимствованный код выводит из-под предела отрицающий
шаблон в `include`, например `!src/generated/**`.

Перед тем как `lexforge-plan` запишет `tasks.md`, он считает строки файлов, которые назовут задачи,
и показывает каждый файл сверх предела. По каждому он задаёт один вопрос: `refactor` возвращает
файл под предел, `keep` оставляет его как есть. Ответ уходит в `.lexforge.yaml` изменения как
`long_files: refactor` или `long_files: keep`.

`lexforge check plan` отказывает плану, который называет длинный файл без записанного ответа
`long_files`. На `refactor` он также отказывает плану, если первая задача, называющая этот файл, не
помечена `(move)`: разбор файла идёт раньше остальной работы над ним.

`lexforge verify` проверяет каждый покрытый файл, который затронуло изменение, по правилу его пути:
на `refactor` каждый тронутый файл укладывается в предел; на `keep` файл, который был в пределе, в
нём и остаётся, а файл, уже бывший длиннее, не прибавляет ни строки. Новый файл укладывается
в предел на любом пути.

## Границы

`check plan` ищет заполнители регулярными выражениями, и фраза вроде «добавить обработку ошибок»,
написанная своими словами, в список не попадёт. Набор расширяется по находкам.

Штамп привязан к коммиту и отпечатку рабочего дерева. Правка после прогона делает его несвежим,
но обратное неверно: штамп не говорит, что покрытие достаточное.

Согласованность реализации с `design.md` машина не считает: отступ от дизайна поймает только скилл
`lexforge-verify`, то есть тот же агент.
