# LexForge

[![lexforge on npm](https://img.shields.io/npm/v/lexforge.svg)](https://www.npmjs.com/package/lexforge)
[![CI](https://github.com/shepaland/LexForge/actions/workflows/ci.yml/badge.svg)](https://github.com/shepaland/LexForge/actions/workflows/ci.yml)
[![license MIT](https://img.shields.io/npm/l/lexforge.svg)](LICENSE)

**Русский** · [English](README.md)

LexForge нужен, чтобы агент соблюдал одни и те же требования к качеству при каждом запуске
и тратил меньше токенов на повторную работу. Он получает контекст своей задачи, сохраняет
результаты проверок и продолжает с места остановки. Девять скиллов проводят его от запроса
до тестов, ревью и архива.

![Агент говорит, что изменение готово; `lexforge verify` отвечает кодом 1, пока проверки не запущены](https://raw.githubusercontent.com/shepaland/LexForge/main/docs/media/verify.ru.gif)

В примере агент написал код и отметил задачи выполненными, но `verify` возвращает `1`,
потому что проверки ещё не запускались. Команда `evidence record` запускает их и сохраняет
результаты. После этого `verify` возвращает `0`.
Файлы примера лежат в [`examples/notes`](examples/notes).

От OpenSpec в LexForge пришли документы требований и порядок работы с ними.
От superpowers взяты правила тестирования и ревью.

Исполнитель и ревьюер получают ещё и инженерные правила для файлов, с которыми работают:
бэкенд, фронтенд, тесты и ревью, плюс добавки для двенадцати стеков. Находка ревьюера называет
правило, которое нарушено. Проект может добавить свои правила, переопределить поставляемые или
отключить правило, указав причину. Подробно в [руководстве по инженерным правилам](docs/engineering-rules.md).

## Быстрый старт

```bash
npm install -g lexforge       # команда нужна скиллам в PATH
lexforge init --tools claude  # agents · claude · codex · cursor · opencode
lexforge doctor               # проверка установки
lexforge stacks set node      # стеки проекта; --none, если ни один из двенадцати не подходит
```

Попросите агента «добавь X» или «почини Y». Скилл `lexforge` определит тип задачи и запустит
подходящий процесс. Подробности настройки есть в разделе [Первый запуск](#первый-запуск).

Общий расход токенов на одинаковых задачах пока не сравнивали.

Обновляйте CLI и скиллы вместе, указав используемые среды:

```bash
npm install -g lexforge@latest
lexforge init --tools claude,codex
```

Установка LexForge 6.0.0 сама не переносит ни одного существующего изменения. Любая
команда на изменении, которое ещё работает на LexForge 5.x, отказывает кодом
`change-needs-migration` и не пишет ничего, пока не прошла миграция:

```sh
lexforge migrate --change <name>
```

Закрытая работа становится историческими задачами, остальное остаётся открытым; ответ
перечисляет незаполненные поля открытых задач в `missingFields`, и открытая часть плана
проходит ревью и подтверждение владельца, прежде чем работа над ней продолжится. Полный
разбор — в [руководстве по исполнению задач](https://raw.githubusercontent.com/shepaland/LexForge/main/docs/task-execution.md).
Остальные изменения совместимости перечислены в [CHANGELOG](CHANGELOG.md).

## Поддерживаемые платформы

| Что нужно | Значение |
| --- | --- |
| Операционная система | Linux, macOS и Windows; тесты запускаются на всех трёх в CI |
| Node.js | не ниже 20.19.0, версия из поля `engines`; в CI 20.19 и 22 |
| Среда агента (рантайм) | `agents`, `claude`, `codex`, `cursor`, `opencode` |
| git | репозиторий хотя бы с одним коммитом и веткой `dev` или `main`; без него `new change`, `evidence record`, `check evidence`, `verify` и `archive` отвечают кодом `2`. Команде `init` не нужен |

На Windows поддерживаются переводы строк CRLF и поиск команд по расширениям из `PATHEXT`.
Пути в ответах записываются с `/`. Обёртка `lexforge.cmd` не считается отдельной установкой.

## Что даёт объединение

LexForge объединяет документы OpenSpec с правилами работы агента из superpowers.
CLI проверяет готовность документов и актуальность результатов тестов перед следующим этапом.

| Взято | Что LexForge с этим делает |
| --- | --- |
| OpenSpec: порядок `proposal → specs → design → tasks` | схема задаёт порядок, `status` показывает готовность; документ со статусом `blocked` писать нельзя |
| OpenSpec: формат требований | `### Requirement:` со сценариями `WHEN`/`THEN`, проверяет `validate --strict` |
| OpenSpec: спецификации в репозитории | `archive` переносит изменения требований в основную спецификацию, а документы задачи в `lexforge/changes/archive/` |
| superpowers: определение типа задачи до проектирования | скилл `lexforge` выбирает исследование (spike) или схему `bounded` / `spec-driven` |
| superpowers: разработка через тесты (TDD) и независимое ревью | `lexforge-apply` проводит тест и независимое ревью каждой задачи |
| superpowers: подтверждение готовности результатами проверок | `evidence record` запускает команду и связывает результат с коммитом и состоянием файлов |

Дополнительно `check plan` ищет заполнители и требования без задач, а `check evidence`
проверяет, не устарели ли результаты запусков. Отключить эти проверки флагом нельзя.
Скиллы получают состояние работы через `lexforge status --change <name> --json`.
Дизайн и план хранятся в каталоге изменения без отдельных копий для каждого скилла.

## Артефакты, ворота, архив

Документы изменения лежат в `lexforge/changes/<name>/`: предложение `proposal.md`,
изменения требований (дельта-спеки), решения `design.md` и план `tasks.md`.
Схема задаёт порядок их подготовки. Проверки между этапами называются воротами (gates).

`check plan` ищет задачи без конкретных действий, ссылки вместо описания работы и требования
без задач. Он также проверяет зависимости разделов и что список `Depends on:` задачи называет
существующие, более ранние задачи, и отмечает две задачи, которые пишут один файл, если между
ними нет цепочки `Depends on:` ни в одну сторону (`shared-file-without-order`). Каждый раздел
плана должен лежать в своём файле, ссылки на них собраны в `tasks.md`.

`task start` открывает рабочее дерево задачи и пишет её инструкцию. В `lexforge/config.yaml`
можно задать `worktree.setup`: команду оболочки, например `npm ci`, которую `task start` один
раз запускает в новом рабочем дереве; при ненулевом коде завершения `task start` удаляет
рабочее дерево и отказывает кодом `worktree-setup-failed`. Если команда задачи ломается, не
добравшись до теста, `task red` отказывает кодом `red-run-broken`: когда в рабочем дереве не
хватает того, что ставит `worktree.setup`, отказ советует задать его; когда разбор называет
модуль, который задача не объявила в `Files:`, отказ советует `lexforge plan amend`.

`task red` записывает запуск падающего теста на тестовом коммите задачи; `task green`
записывает успешный прогон на коммите реализации и пишет пакет для ревью. Если работа по
задаче выходит за дельта-спеку, исполнитель останавливается, называет расхождение со
спекой и ждёт ответа пользователя вместо тихой правки. Команда `evidence record`
запускает проверку проекта и сохраняет её результат вместе с кодом возврата, коммитом и
отпечатком рабочего дерева. Такая запись называется штампом. После правок кода штамп
устаревает; это проверяет `check evidence`.

`verify` читает сохранённые результаты, поэтому проверки нужно запустить заранее. Он также
проверяет, что каждая задача закрыта и прошла ревью, а текущие файлы совпадают с последними
проверенными снимками. Задача включает падающий тест (RED), реализацию, успешный тест
(GREEN) и независимое ревью.

Открытый дефект уровня `critical` или `important` в `lexforge/defects.json` блокирует
`verify` и `archive`. Дефект уровня `minor` можно оставить открытым.
`lexforge defect record --change <name> --level <level> --file <path> --line <n> --summary <text>`
добавляет запись, `lexforge defect close <id>` закрывает её, а `lexforge defect list`
показывает реестр. Флаги `--change` и `--open` отбирают записи. Открытые и закрытые дефекты
сохраняются после архивации изменения.

`archive` вносит изменения требований в `lexforge/specs/<capability>/spec.md` и переносит
каталог изменения в `lexforge/changes/archive/<дата>-<name>/`.
В репозитории остаются актуальные требования и история работы с результатами проверок.

## Установка

Глобальная установка из [npm](https://www.npmjs.com/package/lexforge) добавляет команду в `PATH`,
откуда её вызывают скиллы. Установка в проект закрепляет версию и позволяет вызывать CLI через `npx`:

```bash
npm install --save-dev lexforge && npx lexforge --version
```

При установке только в `devDependencies` команда может быть недоступна в `PATH`.
В таком случае `doctor` сообщает `path-not-resolved`. Если локальная и глобальная установки
указывают на разные пакеты, он сообщает `path-multiple-installs`.

Команда `lexforge init --tools <список>` устанавливает скиллы для сред, перечисленных через запятую.
Флаг `--scope project` ставит их в проект (по умолчанию), `--scope user` в домашний каталог.
Язык документов задаётся через `--language <code>`. Каталоги зависят от среды:

| Рантайм | Каталог в проекте | Каталог пользователя |
| --- | --- | --- |
| `agents` | `.agents/skills` | `~/.agents/skills` |
| `claude` | `.claude/skills` | `~/.claude/skills` |
| `codex` | `.codex/skills` | `~/.codex/skills` |
| `cursor` | `.cursor/skills` | `~/.cursor/skills` |
| `opencode` | `.opencode/skills` | `~/.config/opencode/skills` |

Каталог `agents` могут читать несколько агентов.

## Первый запуск

### 1. Завести рабочее пространство и поставить скиллы

```bash
lexforge init --tools claude
```

Команда создаёт `lexforge/config.yaml`, `lexforge/specs/`, `lexforge/changes/archive/`
и девять каталогов скиллов. Без `--tools` она перечисляет найденные среды и предлагает
выбрать, для каких установить скиллы.

### 2. Проверить установку

```bash
lexforge doctor
```

```
OK    Workspace and configuration
OK    Verification labels
OK    Installed skills
OK    Command name on PATH
OK    Git repository
OK    Node version
Next step: installation is healthy. Ask your agent to start work, for example: lexforge new change <name>
```

В новом каталоге `doctor` сообщит о двух проблемах и вернёт код `1`, если ещё нет репозитория
git и команд в разделе `verification`. Создайте репозиторий через `git init`, сделайте первый
коммит и добавьте свои команды проверки в `lexforge/config.yaml`:

```yaml
verification:
  tests: npm test
  lint: npm run lint
```

Имена меток состоят из строчных букв и дефисов. Команда `evidence record --label tests`
запустит проверку из корня проекта.

### 3. Назвать стеки

```bash
lexforge stacks set node react
```

Команда записывает список в `engineering.stacks` файла `lexforge/config.yaml`. Правила
названных стеков подключаются к общим инженерным правилам; с `--none` действуют только общие.
Двенадцать имён стеков, формат правила и способы добавить, переопределить или отключить
правило описаны в [руководстве по инженерным правилам](docs/engineering-rules.md).
Во время работы эти команды вызывает агент.

## Назначение моделей

В начале каждого скилла есть блок модели с настройками по провайдерам. Для планирования
и проверки завершения указана сильная модель, для реализации и отладки средняя.
Архивация отдельной модели не требует.

Чтобы заменить эти настройки, укажите модели для своих сред в `lexforge/config.yaml`:

```yaml
models:
  tools:
    claude:
      provider: anthropic
      model: claude-opus-5
    codex:
      provider: openai
      model: gpt-5.6-sol
  providers:
    anthropic:
      - claude-opus-5
      - claude-sonnet-5
```

Сначала используется запись среды в `models.tools`. Если её нет, берётся верхний `default`.
Если нет и его, скилл использует модель из собственного блока.

`lexforge init --tools claude,codex` добавляет настройки Anthropic для `claude` и OpenAI
для `codex`, без верхнего `default`. Для `cursor`, `opencode` и `agents` провайдера
и модель нужно указать самостоятельно.

Каталог `providers` заполняется из пакета при установке. Его можно редактировать.
Имена моделей не проверяются по этому каталогу, поэтому новое имя можно указать без
обновления LexForge.

Среда передаётся явно через `--tool`, например
`lexforge instructions <artifact> --change <name> --tool codex --json` или
`lexforge status --change <name> --tool codex --json`.
Без `--tool` команда использует верхний уровень `models`; переменные окружения для выбора
среды не читаются. Если текущая модель не совпадает с назначенной, скилл передаёт работу
субагенту с нужной моделью. Если запустить её нельзя, он останавливается и сообщает причину.

### Проект, поставленный до этой версии

`lexforge init` сохраняет существующий `config.yaml`. Без раздела `models` скиллы используют
собственные настройки. Старые ключи ролей игнорируются. Чтобы назначить свои модели,
добавьте блок выше в `lexforge/config.yaml` и замените имена.

### Передача в каждом рантайме

Возможность запустить субагента на другой модели зависит от среды. Во всех пяти средах
используются одни и те же скиллы.

| Рантайм | Выбор модели для субагента |
|---|---|
| `claude` | Запуск субагента на назначенной модели проверен. |
| `agents`, `codex`, `cursor`, `opencode` | Передача не проверена в этом проекте. До проверки оставьте среду без записи в `models` и используйте модель, указанную в скилле. |

## Девять скиллов

Агент выбирает скилл по полю `description` в `SKILL.md`. Пять скиллов отвечают за планирование.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge` | Просят построить, добавить или починить то, что не входит в существующее изменение | Тип задачи и новое изменение с подходящей схемой |
| `lexforge-propose` | Просят предложение, или `proposal` в статусе `ready` | `proposal.md`: причина, выбранный подход, границы |
| `lexforge-spec` | Просят требования, или `validate` находит дефект в дельта-спеке | Дельта-спеки по возможностям со сценариями `WHEN`/`THEN`, диаграммой и таблицей контракта для взаимодействия, макетом для интерфейса |
| `lexforge-design` | Просят описать решения, схема `spec-driven` | `design.md`, согласованный по одному разделу |
| `lexforge-plan` | Просят план, или `validate` находит дефект в `tasks.md` | `tasks.md`, где задача называет файл и команду проверки |

Пока обязательные документы не готовы, скиллы не переходят к реализации.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge-apply` | Артефакты готовы, просят реализовать | RED/GREEN по каждой задаче плана, с независимым ревью и пакетом для ревью перед закрытием |
| `lexforge-verify` | Реализация закончена, до архивации | Машинные проверки и ревью соответствия требованиям; открытые `CRITICAL` и `IMPORTANT` блокируют готовность |
| `lexforge-archive` | В отчёте нет находок `CRITICAL` | Дельта в `lexforge/specs/`, изменение в архиве, ветка влита в `dev`, вопрос о слиянии в `main` |
| `lexforge-debug` | Падает тест, ломается сборка, код ведёт себя не так | Названная причина, падающий тест на баг, одна правка в точке причины |

Скиллы реализации проверяют `isPlanningComplete`. Работа начинается, когда каждый документ
подготовлен или явно пропущен. `lexforge-debug` можно использовать и без рабочего пространства LexForge.

Не редактируйте установленные скиллы для настройки проекта. `doctor` обнаружит отличие
от версии в пакете, а следующий `init` перезапишет файл. Правила проекта задаются в `context`
и `rules` файла `lexforge/config.yaml` и передаются агенту через `lexforge instructions`.

## Команды и коды возврата

| Команда, после `lexforge` | Что делает |
| --- | --- |
| `init` | Заводит рабочее пространство `lexforge/` и ставит скиллы; `--tools`, `--scope`, `--language` |
| `doctor` | Проверяет локальную установку |
| `migrate --change <name>` | Переносит это изменение на 6.0.0; без `--change` — все изменения и конфиг |
| `new change <name>` | Создаёт каталог изменения, `.lexforge.yaml` и `workflow.json` в новой ветке `feature/<name>` от `dev`; `--schema` меняет схему проекта |
| `status` | Показывает статус артефактов изменения или список активных |
| `instructions <artifact> --change <name>` | Отдаёт шаблон, контекст, правила и инструкцию |
| `validate <change>` | Проверяет артефакты и требования; `--strict` добавляет проверки полноты |
| `check plan --change <name>` | Проверяет полноту плана, зависимости и группы задач |
| `check evidence --change <name>` | Сверяет штампы с кодом на диске; `--require` сужает список меток |
| `evidence record --change <name> --label <label>` | Запускает команду одной метки и пишет штамп |
| `task start --change <name> --task <id> --executor <id>` | Открывает рабочее дерево задачи и пишет её инструкцию |
| `task red --change <name> --task <id>` | Запускает команду задачи на тестовом коммите и записывает падение |
| `task green --change <name> --task <id>` | Запускает команду задачи на коммите реализации и пишет пакет для ревью |
| `task review --change <name> --task <id> --file <report.md>` | Регистрирует отчёт ревьюера по зелёному коммиту задачи |
| `task close --change <name> --task <id>` | Проверяет задачу в git, вливает её в ветку изменения и отмечает галочку |
| `task abandon --change <name> --task <id>` | Удаляет рабочее дерево и ветку задачи, чтобы начать её заново |
| `plan review --change <name> --angle <angle> --file <report.md>` | Регистрирует отчёт ревью плана по одному углу |
| `plan approve --change <name> --quote <words>` | Подтверждает проверенный план словами владельца |
| `plan amend --change <name> --quote <words>` | Принимает правку уже подтверждённого плана |
| `plan escalate --change <name>` | Переводит короткое изменение на полный путь |
| `review final --change <name>` | Пишет пакет финального ревью или регистрирует отчёт ревьюера с `--file` |
| `resume --change <name>` | Восстанавливает состояние из первичных записей |
| `journal add --change <name> --kind <kind> --text <text>` | Пишет запись в журнал изменения; `--quote`, `--reason`, `--scope` |
| `journal resolve --change <name> --id <id> --note <words>` | Закрывает запись журнала с пометкой |
| `journal session --change <name>` | Открывает новую сессию; разрешения прошлой сессии истекают |
| `unlock --change <name>` | Снимает блокировку изменения, оставленную процессом, которого больше нет |
| `verify --change <name>` | Проверяет изменение перед тем, как работу назовут готовой |
| `archive <change>` | Вливает дельту и макеты в спеки, переносит изменение в архив и вливает `feature/<name>` в `dev` |
| `styles find` | Показывает CSS-файлы проекта для макетов |
| `styles set <paths...>` | Сохраняет выбранные CSS-файлы в `ui.styles` файла `lexforge/config.yaml` |
| `stacks set <stacks...>` | Сохраняет стеки проекта в `engineering.stacks`; `--none` сохраняет пустой список |
| `stores add <name> --dialect <dialect>` | Добавляет хранилище данных в `data_stores` файла `lexforge/config.yaml` |
| `rules --change <name> --files <paths...>` | Выводит инженерные правила, которые подходят к файлам задачи |
| `defect record --change <name>` | Записывает дефект по изменению; `--level`, `--file`, `--line`, `--summary` |
| `defect close <id>` | Отмечает записанный дефект исправленным |
| `defect list` | Выводит записанные дефекты; `--change` и `--open` сужают список |

С флагом `--json` команда выводит один документ JSON в стандартный поток вывода,
а сообщения для человека отправляет в поток ошибок. Изменения полей JSON и кодов возврата
перечисляются в [CHANGELOG](CHANGELOG.md).

| Код | Когда |
| --- | --- |
| `0` | Команда отработала, находок нет |
| `1` | Команда нашла нарушение: незакрытую зависимость, требование без сценария, заполнитель |
| `2` | Команду нельзя выполнить: неизвестный аргумент, нет изменения, нет рабочего пространства или репозитория |

Код `1` сообщает о найденном нарушении или непринятом прогоне. Код `2` означает, что
вызов нельзя выполнить; сюда входят устаревшие доказательства и незавершённые условия задачи. У `doctor` одно
отличие: отсутствие рабочего пространства для него находка, поэтому он отвечает `1`, а не `2`.

## Что коммитить

| Путь | Куда |
| --- | --- |
| `lexforge/config.yaml` | В репозиторий: схема, контекст, правила и метки нужны всей команде |
| `lexforge/specs/` | В репозиторий: спеки описывают поведение продукта |
| `lexforge/changes/<name>/` с `evidence.json` | В репозиторий: штамп привязан к коммиту, и в ревью видно, на чём он снят |
| `lexforge/changes/archive/` | В репозиторий: закрытые изменения с артефактами и штампами |
| `lexforge/data/` | В репозиторий: схемы и миграции хранилищ описывают поведение продукта |
| `lexforge/services/` | В репозиторий: документы сервисов описывают сервисы, которые называют спеки |
| `lexforge/rules/` | В репозиторий: свои инженерные правила проекта и переопределения действуют для всей команды |
| `lexforge/defects.json` | В репозиторий: запись переживает изменение, в котором её нашли, а ревью должно видеть, что ещё открыто |
| Каталоги скиллов рантайма и `lexforge-install.json` | Локально: на другой машине их вернёт `init` |

`evidence.json` меняется на каждом прогоне, поэтому два человека, работающие над одним изменением
параллельно, получат на нём конфликт слияния.

## Границы

`check plan` ищет заполнители регулярными выражениями и может пропустить расплывчатую
задачу, написанную другими словами. Правила дополняются по найденным случаям.

Штамп привязан к коммиту и отпечатку рабочего дерева. После правки нужен новый запуск.
Сам штамп не подтверждает, что тесты покрывают всё нужное поведение.

Соответствие кода решениям из `design.md` оценивает агент со скиллом `lexforge-verify`.
CLI не проверяет смысл этих решений.
