# LexForge

## Команды конвейера

| Команда | Что делает |
| --- | --- |
| `lexforge init` | Создаёт каталог `lexforge/` с конфигурацией проекта и ставит скиллы для перечисленных агентов |
| `lexforge new change <name>` | Заводит каталог change и записывает в него схему артефактов |
| `lexforge status` | Показывает статус артефактов одного change или список всех активных |
| `lexforge instructions <artifact> --change <name>` | Отдаёт инструкцию, шаблон, контекст проекта и путь, куда писать артефакт |
| `lexforge validate <change>` | Проверяет артефакты и требования change; флаг `--strict` добавляет проверки полноты |
| `lexforge archive <change>` | Вливает дельту change в `lexforge/specs/` и переносит его каталог в архив |

## Девять скиллов

`lexforge init --tools <список>` кладёт скиллы в каталог названного агента: для Claude Code
это `.claude/skills/`. Дальше агент выбирает скилл сам по строке `description`.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge` | Просят что-то построить, добавить, починить или разобрать, и ни один change этого не покрывает | Названный класс работы и заведённый change с нужной схемой |
| `lexforge-propose` | Просят proposal, или `lexforge status` показывает артефакт `proposal` в статусе `ready` | `proposal.md` из ответов пользователя: причина, выбранный подход, границы |
| `lexforge-spec` | Просят требования и сценарии change, или `lexforge validate` находит дефект в дельта-спеке | Дельта-спеки по возможностям с требованиями и сценариями `WHEN`/`THEN` |
| `lexforge-design` | Просят описать решения и их цену, и change идёт по схеме `spec-driven` | `design.md` из шести разделов, согласованных по одному |
| `lexforge-plan` | Просят план, список задач или разбивку по существующему change | `tasks.md`, где каждая задача называет файл и команду проверки |

Очередь держится на команде `lexforge status --change <name> --json`. Скилл запускает её
первой, находит свой артефакт в поле `artifacts` и смотрит на `status`: работать позволяет
только `ready`. На `blocked` скилл называет неготовые артефакты из `blockedBy` и
останавливается, на `done` показывает готовый файл и спрашивает про перезапись, на `skipped`
называет следующий шаг. Ветки «предупредить и всё-таки записать файл» нет: срок, размер
правки и просьба пропустить артефакт закрытые ворота не открывают.

Вторую половину конвейера ведут четыре скилла.

| Скилл | Срабатывает | Результат |
| --- | --- | --- |
| `lexforge-apply` | Артефакты change написаны или пропущены, просят реализовать | Задачи плана, закрытые по одной: падающий тест, минимальная реализация, ревью субагентом, штамп |
| `lexforge-verify` | Реализация закончена, до архивации | Отчёт по трём измерениям с уровнями находок; одна находка CRITICAL останавливает архивацию |
| `lexforge-archive` | Отчёт проверки без находок CRITICAL, просят заархивировать | Дельта в `lexforge/specs/`, каталог change в архиве, вопрос пользователю про ветку |
| `lexforge-debug` | Падает тест, ломается сборка, код ведёт себя не так, как ожидали | Названная причина, падающий тест на баг, одна правка в точке причины |

Скиллы реализации начинают с той же команды, но читают поле `isPlanningComplete`: пока
хоть один артефакт не написан и не пропущен, работа не начинается. Скилл `lexforge-debug`
этого блока не несёт — баг случается и в проекте, где рабочего пространства LexForge нет.

## Ворота

Четыре команды дают скиллу код возврата вместо обещания, что работа сделана.

| Команда | Что делает |
| --- | --- |
| `lexforge check plan --change <name>` | Ищет в `tasks.md` незаписанные задачи: заполнители, ссылки на соседнюю задачу, требование дельты без задачи, один идентификатор в двух написаниях |
| `lexforge evidence record --change <name> --label <label>` | Запускает команду проверки из конфигурации и записывает штамп: код возврата, коммит, отпечаток рабочего дерева |
| `lexforge check evidence --change <name>` | Сверяет штампы с кодом на диске; `--require` сужает список меток |
| `lexforge verify --change <name>` | Перед завершением проверяет разом незакрытые задачи, требования без следа в коде и несвежие штампы |

Коды возврата те же: `0` — находок нет, `1` — есть хотя бы одна, `2` — проверка не
состоялась: нет git-репозитория, нет change, метка не описана, файл штампов не читается.
Флага, который отключает правило или понижает находку, ни у одной из четырёх нет.

Команды проверок знает проект, а не LexForge. Они описываются в `lexforge/config.yaml`:

```yaml
verification:
  tests: npm test
  lint: npm run lint
```

Имя метки пишется строчными буквами и дефисами. `evidence record --label tests` выполняет
её команду из корня рабочего пространства и печатает вывод по ходу прогона.

Штампы лежат в `lexforge/changes/<name>/evidence.json`, по одной записи на метку. Штамп
привязан к коммиту и отпечатку рабочего дерева, поэтому правка кода после прогона делает
его несвежим, и `check evidence` возвращает `1`.

`verify` штампы читает, а команды проверок не запускает: снятие штампа остаётся за
`evidence record`. Границу своей проверки `verify` называет сам — соответствие кода
решениям `design.md`, полноту требований и качество кода он не измеряет.

## Порядок работы

1. Запрос пользователя разбирает `lexforge`: называет класс работы и заводит change
   командой `lexforge new change <name>`.
2. Артефакты пишутся по очереди — `proposal`, `specs`, `design`, `tasks`, — каждый своим
   скиллом и после `lexforge status --change <name> --json`.
3. `lexforge validate <change> --strict` и `lexforge check plan --change <name>` дают `0`.
4. `lexforge-apply` закрывает задачи плана по одной; на границе задачи снимается штамп
   `lexforge evidence record --change <name> --label tests`.
5. `lexforge-verify` считает машинную часть командой `lexforge verify --change <name>`
   и дописывает то, что машине не поручено.
6. `lexforge archive <change>` вливает дельту в `lexforge/specs/<capability>/spec.md`
   и переносит каталог в `lexforge/changes/archive/<дата>-<name>/`. Команда пересчитывает
   проверки сама: незакрытая задача, требование без следа в коде или несвежий штамп дают
   код `1`, и слияние не начинается.

Отладка встаёт между любыми двумя шагами: `lexforge-debug` срабатывает на падающий тест
и неожиданное поведение, а закончив, возвращает работу тому скиллу, который её передал.

## Коды возврата

| Код | Когда |
| --- | --- |
| `0` | Команда отработала, находок нет |
| `1` | Команда отработала и нашла нарушение: незакрытую зависимость, требование без сценария, оставшийся заполнитель шаблона |
| `2` | Команду нельзя выполнить: неизвестный аргумент, отсутствующий change, битое описание схемы, нет рабочего пространства |

Других кодов нет. Код `1` говорит о проблеме в проекте. Код `2` говорит о неверном вызове.

## Что читает скилл

Состояние change скилл узнаёт из флага `--json` и кода возврата. С этим флагом на стандартный
вывод уходит один документ JSON и ничего кроме него: строки для человека, сообщения о ходе
работы и подсказки печатаются в поток ошибок. Отказ при `--json` тоже приходит документом
JSON с полями `error.code`, `error.message` и `nextStep`.

Формулировки человеческого вывода меняются от версии к версии, разбирать их нельзя. Имена
полей JSON и коды возврата остаются прежними.
