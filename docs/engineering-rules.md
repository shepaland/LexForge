# Инженерные правила

LexForge поставляется с набором инженерных правил: по серверному коду, интерфейсу, тестам, ревью и по двенадцати стекам. Перед циклом исполнитель получает правила, которые подходят к его файлам, а ревьюер проверяет по ним дифф. Этот документ объясняет, как правило устроено и как проект заводит свои правила, переопределяет поставляемые и отключает лишние. Команда `lexforge validate <change> --strict` проверяет формат правил, повторы ID, неизвестные ID, причины отключения и названия стеков.

Правила, которые подходят к файлам цикла, выводит команда:

```bash
lexforge rules --change <name> --files src/billing/invoice.ts tests/billing/invoice.test.ts
```

За один вызов принимается до 200 файлов. Если подошло больше 60 правил, команда отказывает и просит разбить цикл.

## Формат правила

Правило живёт в Markdown-файле. Заголовок третьего уровня задаёт его ID, под заголовком идут четыре поля, по одному в строке:

| Поле | Что в нём |
| --- | --- |
| `Rule` | Что требуется. Не больше 240 символов |
| `Sign` | Что ревьюер увидит в диффе, если правило нарушено. Не больше 240 символов |
| `Applies to` | Глобы файлов в обратных кавычках через запятую. Правило берётся в цикл, если глоб подходит хотя бы к одному файлу |
| `Source` | Откуда правило взято, например `OWASP Top 10 A03`. Если источника нет, ставится `-` |

Названия полей остаются английскими, парсер читает только их. Любое другое поле, пустое поле и лишний символ в ID считаются ошибкой формата.

ID состоит из префикса и двух цифр, например `BE-05`, и не длиннее 16 символов. Префикс выбирает группу правил:

| Префикс | Группа |
| --- | --- |
| `BE`, `FE`, `TS`, `RV` | серверный код, интерфейс, тесты, ревью; действуют всегда |
| `NODE`, `PY`, `JVM`, `GO`, `NET`, `PHP`, `RB`, `RS`, `REACT`, `VUE`, `NG`, `SVELTE` | один стек; действуют, когда стек назван в проекте |
| `P` | правила самого проекта |

Правила `RV` получает только ревьюер, и он получает их для любых файлов, что бы ни стояло в `Applies to`. Остальные правила получают и исполнитель, и ревьюер. Содержимое блоков кода парсер пропускает, поэтому примеры правил в документации ему не мешают.

## Как записать Sign, который виден в диффе

Ревьюер читает дифф. Поэтому Sign описывает то, что можно найти в добавленных строках, без знания остального кода.

Хороший Sign называет конструкцию: «Переменная, склеенная или подставленная в строку запроса, вызов `exec` или путь». Плохой оценивает: «Небезопасная работа с запросами». По первому ревьюер может показать на строку диффа, по второму нет.

- Называйте то, что стоит в коде: вызов, поле, шаблон строки, отсутствие проверки рядом с обращением к данным.
- Если нарушение выражается отсутствием, укажите, рядом с чем его искать: «Запрос по `id` из запроса без условия на владельца».
- Один Sign может перечислять несколько конструкций одного нарушения через `;`. Правило разбивайте, только если в нём два несвязанных требования.
- Если признак не получилось назвать, правило не проверяется на диффе. Перепишите Rule или не заводите его.

## Как переопределить поставляемое правило

Положите в `lexforge/rules/` файл с расширением `.md` и опишите в нём правило под тем же ID, что у поставляемого. Проектное правило заменяет поставляемое целиком, все четыре поля берутся из вашего.

```markdown
### FE-14

- **Rule:** Тексты интерфейса берутся из словаря `src/i18n`, даты и числа форматируются через `Intl`.
- **Sign:** Строка на русском или английском в разметке; дата, собранная вручную.
- **Applies to:** `src/ui/**/*.{tsx,html}`
- **Source:** -
```

Файлы читаются по алфавиту. Один ID описывается один раз. Если он повторяется в одном проектном файле или в двух, `validate --strict` отметит это находкой `engineering-rule-duplicate`. ID, которого нет среди поставляемых и который не начинается с `P-`, даёт находку `engineering-rule-unknown`.

Переопределённое правило стека действует, даже если стек не назван в `engineering.stacks`.

## Как добавить правило P

Правило, которого нет в поставляемом наборе, получает ID с префиксом `P`, например `P-01`. Заведите файл `lexforge/rules/billing.md` (имя любое) и опишите правило тем же форматом. Каталога `lexforge/rules/` после `lexforge init` нет, его создаёте вы.

```markdown
# Правила биллинга

### P-01

- **Rule:** Суммы хранятся целым числом копеек и никогда не считаются во `float`.
- **Sign:** `parseFloat`, `toFixed` или деление суммы на 100 в коде под `src/billing`.
- **Applies to:** `src/billing/**`
- **Source:** -
```

У проекта своя нумерация, следующее правило будет `P-02`. После записи запустите `lexforge validate <change> --strict`. Находки `engineering-rule-format` называют файл, строку и причину.

## Как отключить правило через engineering.disabled

Поставляемое правило, которое проекту не подходит, отключается в `lexforge/config.yaml`. Ключ записи равен ID правила, значение равно причине. Если в конфиге уже есть `engineering` со списком стеков, `disabled` дописывается под тот же ключ:

```yaml
engineering:
  stacks: [node, react]
  disabled:
    FE-14: "Интерфейс на одном языке, словаря нет"
```

Причина не длиннее 200 символов и не бывает пустой. Нарушение даёт находку `engineering-disabled-reason`. ID, которого нет среди поставляемых, даёт `engineering-rule-unknown`. Отключить можно только поставляемое правило. Своё правило `P` отключают удалением из файла.

Отключённое правило не попадает ни к исполнителю, ни к ревьюеру. Причина остаётся в конфиге, и любой, кто прочтёт его позже, увидит, почему правила нет.

## Как назвать стеки командой lexforge stacks set

Общие правила действуют всегда. Правила стека подключаются, когда стек назван в `engineering.stacks`. Пока этого ключа в конфиге нет, действуют только общие правила, а `lexforge status` показывает стеки как `missing`.

Известны двенадцать стеков: `node`, `python`, `jvm`, `go`, `dotnet`, `php`, `ruby`, `rust`, `react`, `vue`, `angular`, `svelte`.

```bash
lexforge stacks set node react
lexforge stacks set --none
```

Первая команда записывает список в `engineering.stacks` и оставляет остальные ключи и комментарии конфига на месте. Вторая записывает пустой список, то есть проект не использует ни один из стеков. Неизвестное имя команда отвергает и называет допустимые. То же проверяет `validate --strict`, находка называется `engineering-stack-unknown`.

## Как править текст правил по no-ai-slop-rus

Текст правил читают и агент, и человек, поэтому пишите их так, как пишут в остальных документах проекта. Если проект ведёт документацию по-русски, правьте Rule и Sign по правилам скилла `no-ai-slop-rus`.

- Пишите действие и предмет. «Суммы хранятся целым числом копеек» понятнее, чем «необходимо обеспечить корректное хранение сумм».
- Вместо «критически важно» и «значительно» ставьте число или убирайте слово.
- Не противопоставляйте то, что никто не утверждал. Пишите прямо, что требуется.
- Держите Rule и Sign в 240 символах. Это предел парсера. Правило, которое в него не помещается, обычно описывает два требования.

Поставляемые правила написаны по-английски. Английский текст правил правят скиллом `no-ai-slop`.

Названия полей `Rule`, `Sign`, `Applies to`, `Source` и ID правила остаются в исходной форме.
