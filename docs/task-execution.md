# Исполнение задач

Единица плана — задача `tasks.md` с полями `Files:`, `Test:`, `Command:` и, когда нужно,
`Depends on:` и `Controls:`. Файл `execution-plan.json` не используется: `tasks.md` и файлы
его разделов — единственный источник плана.

## Как план доходит до реализации

Четыре субагента проверяют план по своим углам — `specs`, `code`, `dependencies`, `gaps` —
и каждый ответ регистрирует `plan review`:

```sh
lexforge plan review --change <name> --angle <angle> --file <report.md>
```

Правка плана после находки отправляет на повторное ревью все четыре угла, не только тот,
что нашёл дефект: CLI засчитывает только отчёты текущего плана, и правка списывает все
прежние одобрения. Когда все четыре угла одобрили текущий план, владелец читает дайджест и
подтверждает своими словами через `plan approve`:

```sh
lexforge plan approve --change <name> --quote "<слова владельца>"
```

## Как исполнитель проходит задачу

Каждый шаг задачи — отдельная команда:

```sh
lexforge task start --change <name> --task <id> --executor <identity>
lexforge task red --change <name> --task <id>
lexforge task green --change <name> --task <id>
lexforge task review --change <name> --task <id> --file <report.md>
lexforge task close --change <name> --task <id>
```

`task start` открывает рабочее дерево задачи и пишет её инструкцию (`brief.md`). В
`lexforge/config.yaml` можно задать `worktree.setup`: команду оболочки, например `npm ci`,
которую `task start` один раз запускает в новом рабочем дереве; при ненулевом коде
завершения `task start` удаляет рабочее дерево и отказывает кодом `worktree-setup-failed`.
Если команда задачи ломается, не добравшись до теста, `task red` отказывает кодом
`red-run-broken`: когда в рабочем дереве не хватает того, что ставит `worktree.setup`,
тестовый прогон не находит тестов или компилятор ошибается вне файлов задачи, `task red`
называет следующим шагом `worktree.setup`; когда в выводе назван модуль, который задача не
объявила в `Files:`, `task red` называет следующим шагом `lexforge plan amend`.
Исполнитель коммитит тест отдельно, затем `task red` запускает команду задачи на этом
коммите и записывает падение. Реализация идёт следующим коммитом; `task green` запускает
команду снова и пишет пакет для ревью. Ревьюер, не писавший задачу, отвечает отчётом, и
`task review` регистрирует его ответ. `task close` проверяет задачу в git, вливает её в
ветку изменения и отмечает галочку.

После закрытия последней задачи `review final` читает весь дифф изменения целиком:

```sh
lexforge review final --change <name>
lexforge review final --change <name> --file <report.md>
```

Первый вызов пишет пакет, второй регистрирует ответ ревьюера. Дальше ход переходит к
`lexforge verify --change <name>` и, если находок уровня CRITICAL нет, к
`lexforge archive <change>`.

## Три выхода на владельца

- `lexforge task abandon --change <name> --task <id>` — для работы, которую написал агент
  не по делу, или для сгоревшего красного прогона: удаляет рабочее дерево и ветку задачи,
  чтобы начать её заново.
- `lexforge plan amend --change <name> --quote "<слова владельца>"` — для задачи, которой
  не хватает в плане: записывает правку после ответа владельца.
- `lexforge plan escalate --change <name>` — для изменения, которое выросло из короткого
  пути: переводит его на полный путь с ревью и подтверждением плана.

## Миграция с 5.x на 6.0.0

Установка LexForge 6.0.0 сама не переносит ни одного существующего изменения. Любая
команда на изменении, которое ещё работает на LexForge 5.x, отказывает кодом
`change-needs-migration` и не пишет ничего, пока не прошла миграция:

```sh
lexforge migrate --change <name>
```

Закрытая работа становится историческими задачами, остальное остаётся открытым. Ответ
перечисляет незаполненные поля открытых задач в `missingFields`, и открытая часть плана
проходит ревью и подтверждение владельца, как любой новый план.
